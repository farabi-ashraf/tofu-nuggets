# 0.4.0 — work order, decisions & rationale

> Planning record for the release that follows 0.3.0. Companion to
> `docs/V0.1.3.md` (which holds the *standing* release policies) and `MEMORY.md`
> (which holds live status). This file is the **why**: what 0.4.0 contains, which
> alternatives were rejected and on what evidence. Status lines live in
> `MEMORY.md`; do not duplicate them here.

## What 0.4.0 is

Three things, shipped as one release:

1. **Fixes for the 0.3.0 badge-layer bugs** on both platforms.
2. **The file-manager update** — the app works inside Windows File Explorer and
   macOS Finder, not only on the desktop.
3. **Small UX debts** from the 0.3.0 backlog.

Driving constraint: **the platform-parity gate** (now binding, written into
`docs/V0.1.3.md`) — no release ships until Windows and macOS both reach the same
usability bar. Consequence knowingly accepted: the macOS 0.3.0 bugs stay in the
wild until the whole set is ready.

## The problem this release exists to solve

0.3.0 drew badges as a coordinate-mapped transparent overlay window on both
platforms. That model broke in platform-specific ways:

| Symptom | Platform | Cause |
|---|---|---|
| Autohide taskbar stopped revealing | Windows | A monitor-covering `WS_EX_TOPMOST` window trips the shell's "fullscreen app" heuristic |
| Empty stray window mid-screen after display sleep | macOS | The overlay panel is *parked off-screen instead of hidden* to keep one window visible; AppKit constrains it back on-screen at wake |
| Dots travel to the active window on "show desktop" | macOS | Coordinate-mapped dot layer follows window geometry, not icon geometry |
| App quits itself when no window is visible | macOS | AppKit terminates on last visible window; that path **skips `ExitRequested`**, so `prevent_exit` never runs |

The architectural conclusion: **stop coordinate-mapping a floating overlay onto
someone else's icon grid**, and let each OS's own mechanism do as much of the
work as it will.

## Decisions

### D1 — Windows desktop badges: keep the layer, fix the heuristic

The GDI layered window stays. `layer_rect()` insets the virtual screen by 1 px
on every side, which is enough to stop the fullscreen-app heuristic from firing.
The `SHAppBarMessage` reveal-strip fallback was designed and **not needed**.

*Known limit left standing*: only the outer virtual-screen edges are inset, so a
monitor in the **interior** of a multi-monitor arrangement is still fully
covered. If the taskbar bug ever appears there, the reveal-strip fallback is the
follow-up.

**Rejected — `IShellIconOverlayIdentifier` (Windows shell overlay handler).**
Re-examined at owner request and rejected a second time:

- 15 overlay slots system-wide, allocated alphabetically; OneDrive and Dropbox
  already consume most of them.
- **One overlay per file, ever.** The owner's own desktop is OneDrive-redirected,
  so every icon already carries a sync overlay — ours would either lose (be
  invisible) or win (destroy sync badges).
- Requires an in-process COM DLL inside `explorer.exe`: HKLM registration (admin
  installer), an Explorer restart per update, and our crash becomes an Explorer
  crash.
- Fixed ~16 px corner glyph — no badge size, corner, colour or theme control.
  Accessibility is core scope, so this alone disqualifies it.

**Rejected — reparenting the layer into the desktop z-band** (`Progman` /
`SHELLDLL_DefView`): already a NO-GO spike (`spikes/badge-reparent`); Win11
26200 does not composite foreign layered windows there.

**Considered and not chosen — dropping `TOPMOST` for `HWND_BOTTOM`.** It would
have deleted the whole per-dot occlusion subsystem (the OS would do occlusion),
but it is unproven on 26200 and the 1 px inset already fixed the bug. Recorded
here so the option is not re-derived from scratch.

### D2 — Inside File Explorer: the pill, not a tracked overlay

A live overlay inside scrolling Explorer windows was rejected on design, before
any code: scroll lag and jitter, viewport clipping of scrolled-out items, and
Win11 tabs plus multi-window churn. Instead, per Explorer window:

- A small glassy **pill**, bottom-right of the *content* area (above the status
  bar, left of the vertical scrollbar, ~12 px inset). The title-bar row was
  rejected — Win11 tabs, search box and ribbon states make it a moving target.
- **Inactive**: shows the count of notes in that window's current folder.
- **Click**: draws dots over annotated *visible* items — a one-shot UIA
  **snapshot**, never live-tracked.
- Dots dismiss on any of: scroll, focus loss, window move/resize, folder
  navigation, tab switch. Toggling the pill again also clears them.

**This is the core design invariant of the feature**: the snapshot model is what
makes all three headaches disappear. Guards are written into the `pill.rs` /
`desktop.rs` `//!` headers and `ARCHITECTURE.md` §7 — *do not "improve" the
snapshot into a tracked overlay*.

Foundations proven by the E0 spike (`spikes/explorer-pill/README.md`, GO on all
three) before any production code: window/tab enumeration, UIA item rects across
all 8 view modes, and the owned-window z-order trick.

### D3 — macOS badges: Finder tags

macOS gets no pill and no overlay window. The app writes a Finder tag named
**`Nugget`** to annotated files; Finder then draws the dot itself — on the
Desktop *and* inside every Finder window, at every zoom level, through every
reshuffle. The badge half of the file-manager update therefore costs nothing on
macOS.

Sidecars remain the source of truth; tags are a derived cue, resynced from
sidecars at startup.

**Rejected for now — `FIFinderSync` extension.** It is the "official" API, but it
needs an Xcode appex target the Tauri bundler cannot embed, a custom CI build and
codesign path, a user visit to System Settings to enable the extension, and it
has unverified interactions with ad-hoc signing. Revisit if tags prove
insufficient, or when an Apple Developer account is bought.

#### Tag collision handling

Tags are a binary-plist array of `"Name\nColorCode"` strings
(`0` none, `1` gray, `2` green, `3` purple, `4` blue, `5` yellow, `6` red,
`7` orange). **Identity is the name, not the colour**: several tags may share a
colour, in which case Finder draws one dot; different colours draw up to three
side by side.

- **Name `Nugget`** — distinctive. Never a reserved colour name ("Orange", …)
  and never something generic like "Note": a *name* collision would mean adding
  and removing a tag the **user** owns, which is far worse than a colour clash.
- **Colour is user-selectable**, via one shared cross-platform `badge_color`
  setting (7 colours, default orange). Windows paints its dot in that colour;
  macOS maps it to the tag colour code. A single setting was chosen over a
  mac-only picker specifically because of the platform-parity gate.
- **No onboarding screen.** A whole first-run flow for one question is scope
  creep and a worse first launch. The real problem — unexplained tags appearing
  on the user's files — is solved by a **one-time notice on the first tag write**
  plus an explainer beside the colour picker.
- **Write hygiene is mandatory**: read-modify-write immediately before writing;
  preserve every foreign entry verbatim including order; **abort and write
  nothing** if the plist fails to parse or holds unexpected shapes; no-op when
  already correct; match ours by exact `"Nugget\n<code>"`; strip any stale
  `"Nugget\n<other code>"` on recolour.
- **Semantics**: tray Pause leaves tags in place (macOS pause affects hover only
  — Finder owns the drawing); the persistent badges-off setting strips the tag
  everywhere and re-tags when switched back on; deleting a note always removes
  that file's tag.

**Documented, not fixed** (two consequences of using the OS's own tag system):
a user's own same-colour tag keeps drawing a dot after our note is deleted, which
can read as "the note survived"; and tags are xattrs, so badge state syncs
between the user's Macs through iCloud Drive or Dropbox.

*Implemented (M4a, PR open, NOT Mini-verified).* New `tags.rs`: pure
tag-array transforms (`with_tag`/`without_tag` — recolour replaces, foreign
entries preserved verbatim, no-op when already correct) plus binary-plist
encode/decode, all unit-tested on every platform (`plist` is a normal dependency
so the safety-net tests run on the Windows dev box); the xattr read-modify-write
and the wiring are macOS-gated. Wired: save adds the tag (unless badges are off),
delete/empty removes it; `set_settings` strips or re-adds across all notes when
the badges toggle flips; startup resyncs from the index (rebuilt from sidecars)
on a worker thread. Colour is read through one helper `tag_color()` (returns 7 /
orange) so **M4b** only swaps its source for the `badge_color` setting. The old
webview badge layer is deleted: `badges_mac.rs`, `app/ui/badges.{html,js,css}`,
the Vite `badges` entry, the `badges` window from `capabilities`, the
`badges:update` event, and the now-dead CG helpers `onscreen_window_rects` /
`display_bounds_pts` (plus their orphaned FFI) in `desktop_mac.rs` — the
`CGWindowListCopyWindowInfo` path that finds Finder's pid stays. M3's delegate
override now carries app survival alone (the always-visible badge window is gone).

### D4 — macOS lifecycle: fix the cause, delete the workarounds

`prevent_exit`, hide-on-close and `ActivationPolicy::Accessory` are all already
in place and all proven insufficient — AppKit's last-visible-window termination
never reaches `ExitRequested`. The remaining documented fallback is the fix:
override `applicationShouldTerminateAfterLastWindowClosed` → `false` on the NSApp
delegate via objc2. Once that holds, the off-screen **panel parking** hack is
deleted (it is the stray after-sleep window), and the always-visible badge webview
window can be removed with it.

**Order hazard**: the badge window is plausibly what keeps the app alive today,
so the delegate override must be hardware-verified **before** the badge layer is
deleted.

*Implemented (M3, PR open, NOT Mini-verified).* New `lifecycle_mac.rs`:
`install()` (called from `main.rs` setup, on the main thread) fetches `NSApp`'s
existing delegate, and `class_replaceMethod`s
`applicationShouldTerminateAfterLastWindowClosed:` → NO onto that delegate's
class via objc2 — the delegate object Tauri owns is extended, never replaced. The
IMP logs each time macOS consults it (the Mini log is the only proof the platform
actually calls it). Parking is fully removed: `overlay::park` is deleted and its
four callers (startup, `hover::hide_panel`, `overlay::hide_overlay`,
`editor::open_editor`) go back to plain `hide()`. The `CloseRequested`
visible-window census logging is **kept** as the discriminator if the exit bug
returns. `objc2` is a `cfg(target_os = "macos")` dependency; the badge webview
window is untouched (M4a). CI (both legs) is the compile gate.

### D5 — Index scope for notes outside the desktop

Decided while building the pill: **known roots**. Every saved note's parent
folder is recorded in `known_roots.json`; the startup index rebuild scans the
desktop dirs plus those roots; roots whose folder is gone are dropped on load.
**The filesystem watcher stays desktop-only** — an unbounded watched set is
exactly the background cost the performance budget forbids.

Rejected: watching every known root (cost); indexing on hover (turns a read path
into a write path); full-disk sidecar scan (minutes, and it indexes other
people's folders on shared machines).

*Residual gap, documented*: renaming or deleting an off-desktop annotated item
while the app runs is reflected only after the next index rebuild.

### D6 — Small UX debts

Checked to-do items render struck through; the main window shows the app
version; a "report bugs / request features" footer points at
`farabigithub@gmail.com` and, on click, reminds the user the app is in active
development. The update dialog already showed the release body verbatim — the
real gap was what we *write* in that body, which became a standing policy in
`docs/V0.1.3.md`.

## Phase order and why it is this order

| Phase | Content | Platform |
|---|---|---|
| W1 | Taskbar-autohide fix (D1) | Windows |
| W2 | Small UX debts (D6) | Windows |
| E0 | Spike: window/tab enumeration, UIA rects, z-order | Windows |
| E1 | Hover + hotkey on Explorer items | Windows |
| E2 | Pill in count mode + known roots (D5) | Windows |
| E3 | Pill click → dots snapshot (D2) | Windows |
| M3 | Delegate override + unpark (D4) | macOS |
| M4a | Tag engine, delete the webview badge layer (D3) | macOS |
| M4b | Shared `badge_color` + first-tag notice (D3) | both |
| M5 | Hover + hotkey inside Finder windows | macOS |

Two rules produced this order:

- **Windows first, all of it.** The dev machine is Windows; macOS behaviour can
  only be tested by the owner sideloading a CI `.dmg` onto the Mac Mini, and
  every new ad-hoc-signed build re-prompts the Accessibility grant. Building
  Windows-side first keeps the expensive test loop for work that genuinely needs
  it, and batches Mini runs.
- **Cause before cleanup.** M3 must be verified before M4a removes the window
  that currently masks the lifecycle bug.

## What the parity bar means here

"The user can see which files have notes, and annotate them, on the desktop
**and** inside the file manager, on both OSes."

The two platforms reach that bar by different mechanisms, which is explicitly
fine: Windows uses a pill with on-demand dots because Explorer draws nothing on
our behalf; macOS uses always-on Finder tag dots and needs no pill at all. The
gate is about what the user can do, not about symmetric implementations.

## Lessons carried out of this work order

- **Spikes can lie by omission.** E0 ran single-tab and in an STA apartment, and
  therefore missed both the MTA `IShellBrowser::GetWindow` failure (`0x8001010D`)
  and the multi-tab active-folder problem that E1 then hit on hardware. Spike the
  *conditions the product will run in*, not just the API.
- **Isolate before claiming a performance number.** Whole-process CPU here is
  dominated by the badge layer's UIA walk, so the same build reads 0 ms or 250 ms
  per 25 s depending only on whether the desktop is covered. The pill's real cost
  was measurable only by building without it.
- **Modern Explorer content is a `DirectUIHWND`.** List items are not real child
  windows, so neither `LVS_EX_INFOTIP` suppression nor wheel-scroll window events
  work there; scroll dismissal needed a `WH_MOUSE_LL` hook installed *only while
  dots are shown*.
- **An owned popup sits above its owner only until the owner is re-activated.**
  Every automated repro masked this by calling `SetForegroundWindow`. Re-insert
  the window just above its owner on each render — never `HWND_TOP`, which would
  float it over unrelated apps.
